> 用户三点反馈：①B 组（d25/d50）也进面板；②A 组 9 个为什么不能并排跑——机器没用满；③cube 现在就开始，充分利用机器。
> 本版改动：三 lane 并行架构、B 组 18 runs 进队列、cube 立即启动、统一面板。判据与冻结清单全部不变（上承 OGBcube迁移计划-20261104 + HANDSHAKE §4-5）。

## 0. 为什么之前是串行 + 现在为什么可以并行（回应反馈②）

之前串行是两个保守假设：mac 上"3 进程抢 mps 慢 3.5×"的教训平移过来 + 150 envs 的 CEM 显存峰值未知。**刚才实测推翻了顾虑**：

| 资源 | 实测 | 结论 |
|---|---|---|
| CPU | Ryzen 9 7945HX，**16 核 32 线程** | 3-4 个 lane 各占 1-2 核无压力 |
| 显存 | 单 run 全程 **~1.5GB / 8GB**（含 150-env CEM 轮） | 3 lane ≈ 4.5-6GB，放得下 |
| GPU 利用率 | 单 lane ~35% | 3 lane ≈ 饱和 |
| 已验证 | run 1 flat(5,5) d75 s42 n=150 已落盘 **17.33%**（26/150，pilot 16.0% 同量级，管线 sanity 过），35 分钟/run（含 ~20min 抽样段） | — |

**并行安全性的根据**：每个 run 是独立进程（torch RNG 各自随机），配对性来自 numpy 抽样（seed 决定，与并发无关），互不干扰。

## 1. 三 lane 并行架构（总调度）

```
lane A（已在跑）: run_taskA.py 顺序跑 A 组剩 8 个（d75 决定性三角）
lane B（批准后立即启动）: PushT B 组 18 个（见 §2）

夜间收尾: A+B 全部落盘后 → e6_eval 参数化 + pusht smoke 回归 → cube E6 12 个
```

- **显存守卫**：lane B/C 的 runner 每 run 启动前查 `nvidia-smi` 空闲显存，< 2.5GB 就等待重查（防峰值叠加）
- **e6_eval.py / probe_t_policy.py / boundary_policy.py 编辑冻结线**：lane A/B 任何 run 还没跑完就不许编辑（runner 每 run 重新读盘）。cube E1 只用 flat 臂 + 数据补丁 + cube.yaml，**零编辑**即可跑；需要编辑的只有 cube E6 的四臂接线（夜间冻结线解除后做）
- 面板：统一 `runs_dashboard.html` 读 taskA/taskB/taskC 三个 data.js（§6）

## 2. lane B：PushT B 组 18 runs（回应反馈①）

**b2 判据需要**：对每个 d∈{25,50,75} 取 argmax over {5,10,15}（预注册）。d75 的 {5,10} 两臂由 A 组出（n=150×3seeds），所以 B 组补齐：

| d (budget) | 臂 | 说明 |
|---|---|---|
| 25 (50) | flat(5,5), flat(10,10) | **flat(15,15) 结构上不可能**：e6_eval 断言 `receding×block ≤ budget`，15×5=75 > 50，跑不了（这本身就是论点：短目标距离下长平坦视野连一个计划都执行不完） |
| 50 (100) | flat(5,5), flat(10,10), flat(15,15) | 15×5=75 ≤ 100 ✓ |
| 75 (150) | flat(15,15) | 补齐 d75 三臂的第三臂（pilot 只有 n=50 s42=14.0%），A 组已出 {5,10} |

合计 (2+3+1)×3 seeds = **18 runs**，n=150，命名 `flat_h{H}r{R}_d{d}_s{seed}_n150.json`。d25/d50 的 run 更快（budget 50/100 → 每 ep 重锚轮数少），预计 15-25 min/run。

## 3. cube 立即启动：阶段 0（现在，纯 CPU，与 A/B 并行）

> 已探明关键事实：cube h5 缺 `episode_idx`（e6_eval 直接 KeyError）和 `privileged_block_0_pos/quat`（cube.yaml callables 引用）——但都能从已存列推导补上，**不用重采集**。

1. **`src/patch_cube_h5.py`**：h5py 'a' 模式加 3 列（只加不删，秒级）：`episode_idx`（ep_offset/ep_len repeat）、`privileged_block_0_pos`（qpos[:, adr:adr+3]）、`privileged_block_0_quat`（qpos[:, adr+3:adr+7]）；`adr` 由实例化一次 OGBCube env 拿 `object_joint_0` 的 jnt_qposadr（scene_env L1098 证实 block 位姿就是该 free joint 的 qpos 切片）。自洽验证：success=True 帧附近 block 趋停。
2. **`ogb_cube_events`**（fit_features.py 新函数，kinematic_events 不动）：block 位移阈值 + 持续帧去抖（manip_onset ≥2 帧 / pose_settle ≥3 帧），thresh 由全数据位移分布双峰/肘部数据驱动校准（落盘 `runs/cube_event_thresh.json`），帧 t → 模型步 t-1 对齐；`runs/cube_event_check.png` 2 条轨迹叠加目检。
3. **节律谱系验证（第一关卡）**：`runs/rhythm_spectrum.{json,png}`，PushT push/settle 间隔（重算 100 eps）vs cube manip/settle 间隔（500 eps），方差/CV/重尾。**PASS 才进 lane C 的 E1；FAIL → 停 + 汇报**（预案按 20261103 §4）。
4. **cube.yaml 适配**（任务 A/B 不用它，安全）：`keys_to_cache: [action, qpos, qvel]`；callables 维持 `set_state(qpos,qvel)` + `set_target_pos(cube_id=0, target_pos=goal_privileged_block_0_pos, target_quat=goal_privileged_block_0_quat)`（补丁后列存在）。
5. **cube E1 smoke**（GPU 5 分钟，num_eval=2）：验证 MUJOCO_GL 后端（e6_eval setdefault 'egl'，Windows 上 mujoco 若拒 → 启动前 `$env:MUJOCO_GL` 预设绕过 setdefault）、150→2 envs、callables 生效。
6. **cube 版代码**（新文件不动 pusht 原件）：`e2_extract_features_cube.py`（H5=cube h5、CKPT=cube/weights.pt、OUT=features_cube/、N_EPS=500、SEED=0、state 列→qpos；checkpoint config 已证 input_dim=25=5 维动作×block5、num_frames=3 与 pusht 同构）、`r2_dualhead_cube.py`（标签源=ogb_cube_events，500 eps 按 seed=0 划 400/100，输出 models_cube/{head_r2_dual_cnn.pt, r2_meta_dual_cube.json, fz_dual_linear_cube.npy}，路径写本机相对路径）、`test_deploy_align_cube.py`。

## 8. 风险与预案

| 风险 | 预案 |
|---|---|
| 3 lane 显存峰值叠加 | runner 级显存守卫（<2.5GB 空闲等待）；实测单 run 1.5GB，余量大 |
